Draft implementation sequence — 2026-11-23

1. M0: Verify both ACP worker routes in isolated fixtures. Resolve whether ChatGPT means Codex or the app. Record versions, authentication, streaming, cancellation, permissions and resume capability.
2. M1: Build one supervised task end to end. Keep provider transport behind a small adapter and enforce chosen permissions outside the model. Begin with one worker per workspace.
3. M2: Add scoped durable conversation memory and bounded handoff context. Separate user preferences, project facts, summaries, task state and planning records.
4. M3: First specify workspace-scoped typed input using Mastra Signals (MAST-45); then persist worker lifecycle, reconcile interruptions, prevent duplicate dispatch, bound retries and report evidence. Do not blindly replay unknown side effects.
5. M4: Add plantool operations, bounded lookups and inspectable Agent Skills. Reuse worker-native tooling.
6. M5: Run deterministic failure tests, opt-in live tests and a short user pilot before expanding.

Architecture proposal: interaction surface -> Mastra supervisor and per-thread Signals -> bounded tools and worker adapter -> Cursor / confirmed OpenAI worker. Use sendMessage for user prompts; queueMessage or queueSignal for ordered follow-ups; sendNotificationSignal for durable asynchronous worker/CI events with source, kind, payload and idempotency/coalescing keys. Use transient/reactive or state signals only for request-scoped or thread context, not as a durable event inbox. Notifications require supported storage and a notification inbox tool to expose stored payloads to the model. Mastra queues are per thread; define a stable workspace resourceId and an explicit target thread policy for workspaces with multiple conversations. Persist inputs whose loss is unacceptable because in-memory runtime queues are lost on process crash. With multiple server processes, configure shared PubSub/leases; the current single-process local prototype can use the default in-process transport. The application task store remains authoritative for worker lifecycle, approvals and side-effect reconciliation; Plantool .plan holds goals, decisions and planned/completed work. Context assembly, permissions, endpoint authentication and webhook verification are explicit application services. No separate orchestration platform is needed for this first loop.

Review order: top-level goal, recorded decisions (none open as of 2026-11-24), M0 compatibility tasks, then milestone acceptance criteria and dependencies. Ticket dependencies control readiness; open person-owned choices block only affected work. Future candidates are labelled later,not-mvp and wait for the pilot.

Current evidence: Cursor CLI 2026.11.17-f532c45 exposes agent acp; a later build 3.29.9 was also probed on 2026-11-23. Installed Codex is 0.171.0-alpha.13. These are local version/help checks only, not authenticated integration results. Official Cursor docs describe native ACP; the maintained Codex ACP adapter describes a Codex App Server bridge with ChatGPT login. Direct ChatGPT-app ACP support is unverified. Pin actual tested versions during M0.
